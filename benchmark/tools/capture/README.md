# Engine showcase capture

`prepare_ffmpeg.py` downloads the SHA-256-pinned Windows FFmpeg 8.0.1 distributor archive into ignored `benchmark/local/capture/`. Python, network access and the `7z` command are required. The existing RTX 2060 driver passed a one-second NVENC synthetic encoder check with this version. FFmpeg 9.0.2 failed because it required a newer NVENC API. These capability checks are not game footage or performance measurements.

Windows Graphics Capture is now the default, following an actual successful Unity recording after GDI returned a frozen Direct3D surface. Build the explicit-window helper once with `Build-WindowCapture.ps1`. Launch one actual packaged engine demo in its showcase/wait mode under the shared heavy-task guard, then run the recorder from a separate PowerShell process, passing the real game process ID:

```powershell
.\benchmark\tools\capture\Capture-Demo.ps1 `
  -Engine Unreal -GameProcessId <actual-game-pid> `
  -RuntimeLog .\benchmark\unreal\evidence\runtime.log `
  -StartFlag .\benchmark\unreal\evidence\showcase-start.flag `
  -EngineAudio .\benchmark\unreal\evidence\showcase-engine-audio.wav `
  -OutputDirectory .\benchmark\unreal\evidence\showcase-review-01
```

For Unity, supply its corresponding runtime log, gate and game-only WAV paths with `-Engine Unity`. The recorder waits for the scene's `SHOWCASE_READY` marker, starts client-area capture of the explicit game HWND, then writes the gate. It records the 72-second timeline, waits for `SHOWCASE_COMPLETE` and the exported engine-only WAV, and muxes an H.264/AAC MP4. It does not capture desktop/system/microphone audio or change OBS configuration. The game remains running after capture. Existing final videos and WAV files are preserved; use a fresh output directory and archive task-owned audio before another recording.

The 30 fps recording rate is not a claim about engine frame rate. Run performance sampling separately. Capture aborts if its target loses foreground, minimizes, closes or changes client size. Before muxing, it compares known wide/action/portrait cues in a downsampled central viewport using pixel differences, checks the entire recording for five-second frozen plateaus, rejects any interval of at least one second with 98% near-black pixels, and rejects an empty/silent engine WAV using measured sample count, peak and RMS levels. The motion detector was executed against the rejected GDI recording and correctly found a 74.833-second frozen plateau despite small compression differences. Its thresholds remain a review gate, not proof of faithful animation. Raw media remains available on failure; no desktop fallback is used. The detectors passed small synthetic black/signal/silence checks. The first actual Unity GDI recording failed motion review: it encoded a frozen Direct3D surface despite nonblack pixels and nonzero engine audio. Frames at 26, 31 and 41 seconds were byte-identical, and both the wide opening and portrait cue still showed the initial idle view. The resulting MP4 is rejected evidence, not a demo video. Evidence is preserved in ignored `benchmark/local/evidence/unity-showcase/20261006-024245/capture/`. The subsequent actual WGC run passed these technical capture checks; Unreal recording remains pending. It produces a JSON report, logs, source video, final MP4 and extracted review frames. Audio alignment uses the first captured-frame UTC timestamp and the engine's recording-start UTC from its log or `showcase-started.json`; gate-time fallback is explicitly recorded. Audio-thread latency and frame rounding still require listening review. Inspect motion, occluded frames and sound synchronization before accepting the result. Successful muxing alone does not establish visual acceptance.

Implementation references: [FFmpeg's Windows client-area capture source](https://github.com/FFmpeg/FFmpeg/blob/n8.0.1/libavdevice/gdigrab.c), [verified distributor release](https://github.com/GyanD/codexffmpeg/releases/tag/8.0.1).

The explicit-window WGC backend is the verified path on this reference machine. Build it with `Build-WindowCapture.ps1`, then record in a fresh evidence directory; `-CaptureBackend WGC` may be supplied explicitly. `-CaptureBackend GDI` remains available for scoped diagnostic work, but its known frozen output is not usable demo evidence. The recorder never silently repeats a recording. The native helper uses only `CreateForWindow` with the validated HWND and owner PID, checks foreground/size throughout, and requires the intended borderless client dimensions to match the captured surface. It never calls monitor/desktop capture. Windows' capture border remains enabled. This path currently supports the demos' SDR BGRA8 output.

WGC sends real-time BGRA frames through a local named pipe to the same NVENC encoder. Its metadata records frame and repeated-frame counts, first scheduled output UTC and the first compositor-frame UTC. The constant 30 fps video repeats the latest image only when the compositor supplies no newer frame; this does not imply 30 unique game frames per second. A capture that falls more than half a second behind its real-time schedule fails with its partial media preserved. The recorder aligns engine audio to the first scheduled video-frame UTC, retains the same black/silent-media checks, and still requires visual and listening review. The native helper compiled successfully against MSVC 14.44/Windows SDK 10.0.26100 and has now captured the actual running Unity game successfully.

WGC implementation references: Microsoft's [single-window capture interop](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [capture-frame polling and SDR format guidance](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture), and [compositor QPC frame timestamps](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe.systemrelativetime).
